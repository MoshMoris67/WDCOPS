# WellcashOps demo deployment

A neutral, country-free copy of WellcashOps for pitching to other Wellcash branches.
It runs from the **same code** as the Uganda system; what makes it a demo is its
settings and its own database. The Uganda system is not affected.

> **Fake data only.** The demo database must never hold real client or debtor data
> (the schema's own header says real client data stays on a self-hosted Postgres).
> Anything shown to other countries is generated by `prisma/seed-demo.js`.

## How the demo differs from Uganda

| | Uganda (real system) | Demo |
|---|---|---|
| Runs on | the office server (Docker) | Render |
| Database | the office Postgres | its own Neon database (fake data) |
| `NEXT_PUBLIC_DEMO_MODE` | not set | `true` |
| Branch label | Uganda | Demo |
| Currency | UGX | USD |
| Accounts | `@wellcash.ug` | `@demo.wellcash.com` |
| Source maps | on | off |

All the differences live in `src/config/deployment.ts`. With the variable unset the
code behaves exactly as it did before that file existed.

## Setting up the demo on Render

1. **Database:** a Neon project for the demo only. Use the direct connection string
   (no `-pooler` in the host).
2. **Render environment variables** (Service > Environment):

   | Name | Value |
   |---|---|
   | `NEXT_PUBLIC_DEMO_MODE` | `true` |
   | `DATABASE_URL` | the demo Neon string |
   | `SESSION_SECRET` | a new random value, different from the office server's |
   | `WORKER_SECRET` | a new random value (also set as a GitHub Actions secret for the tick) |
   | `NODE_VERSION` | `22` |

   `NEXT_PUBLIC_*` values are baked into the build, so set the variable **before**
   deploying, or redeploy after adding it.
3. **Build / start commands:** unchanged (`npm install && npm run build`, `npm start`).
   The build applies the database migrations.
4. **Fill the database with demo data** (this ERASES everything in it). From any computer
   with the repository and Node:

   ```bash
   npm install
   DATABASE_URL='postgresql://...neon.tech/...' \
   DEMO_SEED_CONFIRM=wipe-demo-database \
   npm run seed:demo
   ```

   The script refuses to run unless `DEMO_SEED_CONFIRM` is set **and** the database host
   ends in `neon.tech` (override with `DEMO_DB_HOST_SUFFIXES`, comma separated), so it can't
   be pointed at the office server by accident.
5. **Log in** as `admin@demo.wellcash.com`. For now every demo account's password is its own
   email address (agents: `amina.hassan@demo.wellcash.com`, `tendai.moyo@...`, and so on).
   Change this before sharing the link widely.

## What the seed creates

2 admins and 8 agents, 4 fictional clients (one with commission rates), about 640 debtors
(amounts in USD) with assignments, roughly 1,100 call logs spread over the last two
weeks, promises to pay, callbacks, and a processed reconciliation per client. 40 debtors in a
top-up file are left unassigned so auto-distribution can be shown. Dates are relative to the
day you run the seed. Running it again resets everything to the same starting state.

## Keeping Uganda safe

- The office server never sets `NEXT_PUBLIC_DEMO_MODE`, so a `git pull` and rebuild there
  gives it the same behaviour as before: UGX, the Uganda text, `@wellcash.ug`.
- The demo and office copy use separate databases. Deploying a migration to one does not
  update the other: Render's build applies migrations to the demo Neon database, and the
  office Docker build applies migrations to the office Postgres database. Deploy and verify
  schema changes for both copies separately, using each copy's own `DATABASE_URL`.
- Before updating the office server, note the commit it is on (`git rev-parse HEAD`). To roll
  back, `git checkout <that commit>` and rebuild.
- `npm run check:deployments` builds both versions and fails if the demo build contains any
  country-specific text, or if the Uganda build lost its own. Run it before merging changes.

## Currency switcher

The demo shows a **Currency** control next to the theme toggle in the sidebar (and in the top bar
on phones, and on the login page). Choices: USD, EUR, MZN, KES, TZS, ZMW, ZAR, AED and ZWG.

- Amounts are stored in **USD**. Switching currency only changes how they are *shown*: stored
  amount x rate. The choice is remembered in the browser; the page may show USD for a
  fraction of a second on load before the saved currency applies.
- The rates are **fixed, indicative figures**, not live. They live in
  `src/config/currencies.ts`; edit that file and redeploy to refresh them. The dropdown says so.
- Entry fields (promised amount, manual payment) and Excel downloads stay in USD and are labelled
  that way, so what is typed or exported is never ambiguous.
- The Uganda system has no switcher and prints UGX exactly as before.

## Importing files in another currency

The demo stores everything in USD. The upload screens (Import New File, Sync Update and Log
Reconciliation) therefore have an **"Amounts in this file are in"** selector. Pick the file's
currency and every amount in it (balances, payments, commissions) is converted to USD once, when
the file is imported, at the indicative rates in `src/config/currencies.ts`.

- The list is the nine display currencies plus UGX (accepted on upload, never shown as a display
  choice). Edit `IMPORT_CURRENCIES` to add more.
- The converted amount is stored; changing the rates later does not re-convert old files.
- Other columns kept as "Additional Info" (for example a disbursed amount) are shown as typed in
  the file, in its original currency.
- Pick the right balance column in the mapping step (for example "Loan Bal." rather than
  "Disb. Amt").
- The Uganda system has no selector and stores amounts exactly as the file gives them.
- The demo's balance bands are set for dollar amounts, so convert before distributing.

## Language switcher

The same menu (globe icon, "Language and currency") offers **English, Portuguese (Mozambique),
Swahili and Shona**. The choice is remembered in the browser and applies to screens, buttons,
messages and dates.

- How it works: English text in the code is the lookup key. `t('English text')` returns the
  translation from `src/i18n/dict/<code>.json` (`pt`, `sw`, `sn`), or the English text itself if
  there is none, so nothing is ever blank. On the Uganda system `t()` returns the English text
  untouched.
- **The translations are a first draft for review**, especially Shona. They are in
  `translations/pt.csv`, `sw.csv`, `sn.csv` (columns: English, translation, where it is used).
  Have the Mozambique, Kenya/Tanzania and Zimbabwe teams correct them, then load the corrected file:
  `node scripts/i18n/i18n.mjs import pt translations/pt.csv` (same for `sw`, `sn`), and
  `node scripts/i18n/i18n.mjs check` to validate. `report --missing` lists anything untranslated.
- New screen text: wrap it in `t('...')`, run `node scripts/i18n/i18n.mjs report --missing`, and
  add the translations (or re-export the CSVs for the reviewers). Text shown through a variable
  (for example a table header array) cannot be found automatically: add it to
  `src/i18n/indirect-keys.json`.
- Dates follow the language (`pt-MZ`, `sw-KE`; English and Shona use day-first `en-GB`, as browsers
  have no Shona date data). Debtor names, client names and call notes are data and are never
  translated. Disposition names are translated when the text matches a known one.
- Exports (Excel downloads) stay in English.
- The Uganda system has no switcher and is unchanged.
