# WellcashOps demo deployment

A neutral, country-free copy of WellcashOps for pitching to other Wellcash branches.
It runs from the **same code** as the Uganda system; what makes it a demo is its
settings and its own database. The Uganda system is not affected.

> **Fake data only.** The demo database must never hold real client or debtor data
> (the schema's own header says real client data stays on a self-hosted Postgres).
> Anything shown to other countries is generated by `prisma/seed-demo.js`.

## How the demo differs from Uganda

| | Uganda (real system) | Demo |
|---|---|---|
| Runs on | the office server (Docker) | Render |
| Database | the office Postgres | its own Neon database (fake data) |
| `NEXT_PUBLIC_DEMO_MODE` | not set | `true` |
| Branch label | Uganda | Demo |
| Currency | UGX | USD |
| Accounts | `@wellcash.ug` | `@demo.wellcash.com` |
| Source maps | on | off |

All the differences live in `src/config/deployment.ts`. With the variable unset the
code behaves exactly as it did before that file existed.

## Setting up the demo on Render

1. **Database:** a Neon project for the demo only. Use the direct connection string
   (no `-pooler` in the host).
2. **Render environment variables** (Service > Environment):

   | Name | Value |
   |---|---|
   | `NEXT_PUBLIC_DEMO_MODE` | `true` |
   | `DATABASE_URL` | the demo Neon string |
   | `SESSION_SECRET` | a new random value, different from the office server's |
   | `WORKER_SECRET` | a new random value (also set as a GitHub Actions secret for the tick) |
   | `NODE_VERSION` | `22` |

   `NEXT_PUBLIC_*` values are baked into the build, so set the variable **before**
   deploying, or redeploy after adding it.
3. **Build / start commands:** unchanged (`npm install && npm run build`, `npm start`).
   The build applies the database migrations.
4. **Fill the database with demo data** (this ERASES everything in it). From any computer
   with the repository and Node:

   ```bash
   npm install
   DATABASE_URL='postgresql://...neon.tech/...' \
   DEMO_SEED_CONFIRM=wipe-demo-database \
   npm run seed:demo
   ```

   The script refuses to run unless `DEMO_SEED_CONFIRM` is set **and** the database host
   ends in `neon.tech` (override with `DEMO_DB_HOST_SUFFIXES`, comma separated), so it can't
   be pointed at the office server by accident.
5. **Log in** as `admin@demo.wellcash.com`. For now every demo account's password is its own
   email address (agents: `amina.hassan@demo.wellcash.com`, `tendai.moyo@...`, and so on).
   Change this before sharing the link widely.

## What the seed creates

2 admins and 8 agents, 4 fictional clients (one with commission rates), about 640 debtors
(amounts in USD) with assignments, roughly 1,100 call logs spread over the last two
weeks, promises to pay, callbacks, and a processed reconciliation per client. 40 debtors in a
top-up file are left unassigned so auto-distribution can be shown. Dates are relative to the
day you run the seed. Running it again resets everything to the same starting state.

## Keeping Uganda safe

- The office server never sets `NEXT_PUBLIC_DEMO_MODE`, so a `git pull` and rebuild there
  gives it the same behaviour as before: UGX, the Uganda text, `@wellcash.ug`.
- No database migrations are involved, so pulling and rebuilding does not touch the office
  database structure.
- Before updating the office server, note the commit it is on (`git rev-parse HEAD`). To roll
  back, `git checkout <that commit>` and rebuild.
- `npm run check:deployments` builds both versions and fails if the demo build contains any
  country-specific text, or if the Uganda build lost its own. Run it before merging changes.
